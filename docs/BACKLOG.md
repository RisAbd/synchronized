## 🔴 Архитектура: обезличенный аллайнер + маппинг двух редакций (указка владельца 11.07, сессия 9)

> Контекст: П9 (турецкий мусхаф Diyanet) → выяснили, что текст Diyanet реально другой в Unicode и с
> ДРУГИМ дроблением слов (8/62 аятов на Ан-Наджм). Владелец выбрал «третий путь»: не заменять и не
> дублировать forced на каждый текст, а (1) замапить две редакции по индексам + переключать; (2)
> сделать аллайнер «обезличенным» — не привязываться к началу/концу аятов, обрабатывать текст
> СПЛОШНЯКОМ (стеной), а разбивку на аяты навешивать отдельным слоем.

**Задача B — аллайнер «стеной» (boundary-free).** ЦЕЛЬ: аллайнер выравнивает ПЛОСКИЙ поток слов к
аудио, ничего не зная про аяты; (surah,ayah,wi) — чистые метки-лейблы поверх плоского индекса.
- ✅ Хорошая новость: `falign.align` УЖЕ по сути стена — склеивает весь текст аятов в одну строку,
  гонит CTC непрерывно, потом лейблит слова (surah/ayah/wi). Повторы теперь тоже кросс-аятные (сессия 9).
- Что реально «смотрит на аяты» и требует переосмысления: (а) `align.py` (ASR-консенсус, легаси) —
  определяет ДИАПАЗОН аятов, ayah-aware; (б) `falign.verses_from_data` — обрезает краевой аят по
  покрытию (per-ayah); (в) `timeline` (старты аятов) — производная, ок как метка.
- План: ввести ПЛОСКИЙ word-index как первичный ключ выравнивания; (surah,ayah,wi) → таблица-лукап от
  плоского индекса. Это же — фундамент для Задачи A (маппинг редакций по плоскому индексу).

**Задача A — маппинг двух редакций текста (Tanzil ↔ Diyanet) по индексам + переключение.** Обе
редакции — один Коран (те же аяты/чтение), отличаются диакритикой и ЧАСТИЧНО дроблением слов.
- Маппинг считаем ОФФЛАЙН (оба текста статичны): по аятам (границы аята общие, даже если дробление
  слов внутри разное) выравниваем плоские последовательности слов через согласный СКЕЛЕТ (как в
  align/falign) → карта Tanzil-word-idx ↔ Diyanet-word-idx (1↔1 и 1↔many на 8 «разошедшихся» аятах).
- Выравниваем аудио на ОДНОЙ редакции → тайминги на плоском индексе; для показа ДРУГОЙ редакции слово

- 🟡 **Масштабирование обработки МЕЖДУ записями — через ОЧЕРЕДИ CELERY, не код-лок (уточнено
  владельцем 12.07).** Внутри записи ASR уже параллельны. Но celery `--concurrency 1` → две записи
  идут строго по очереди; хочется, чтобы облачный google записи B молотил, пока GPU занят записью A.
  **ПРАВИЛЬНЫЙ подход (портируемый, конфигом):** раздельные очереди `task_routes` (gpu/default) +
  два воркера `celery -Q gpu --concurrency 1` и `-Q default --concurrency N`. «Только по 1» на GPU =
  свойство ДЕПЛОЯ (сколько gpu-воркеров с какой concurrency), а не зашитый в бизнес-логику лок — на
  большой карте просто `-Q gpu --concurrency 4`, код не трогаем. Плюс `rate_limit`/`task_annotations`.
  **НЕ делать `filelock`/семафор в pipeline** (я так пробовал 12.07 — владелец справедливо отверг:
  concurrency=1 это свойство ЕГО 6ГБ-карты, в других средах иначе; в коде хардкодить нельзя).
