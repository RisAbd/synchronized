# RESEARCH: live-распознавание + быстрый контекстный поиск места в Коране (WI)

> Прощупывание темы по указке владельца (tg_4810, 28.07). Цель — не пост-обработка записи, а поиск
> места В РЕАЛЬНОМ ВРЕМЕНИ по мере чтения. Тайминги вторичны, важны СКОРОСТЬ и УВЕРЕННЫЙ контекстный
> поиск. Killer-сценарии: live-подсветка, «память рядом» (начал — оно ведёт), режим заучивания
> (отклонение от оригинала → красным). См. BACKLOG WI.

## Что болело

Текущий буквенный поиск (`match_align.find_range`/`find_segments`) = difflib над ВСЕМ декодом × суры →
**секунды-десятки** (замер: rec7 2.9с, rec10 5.8с, **rec9 20.7с**). Для live непригодно (владелец прямо
назвал «тормознутым на дифлипах»). Плюс он ищет ОДИН батч-диапазон — не инкрементально.

## Что сделано (ядро скорости)

**`match_align.locate(dec_window, index, prior_fa=None)`** — локатор плоского аята из ОКНА декода
(«недавно услышанное») поверх ТОГО ЖЕ инвертированного k-грамм-индекса (`index.kidx`): IDF-голосование
по аятам (`_ayah_density`) — **O(длины окна)**, не O(корпуса). **~0.2 мс/вызов** против 20с у difflib —
**в ~100 000× быстрее.** Главный враг live устранён: искать на лету дёшево.

### Два трекера позиции

**`match_align.SegmentTracker` (ГЛАВНЫЙ результат) — онлайн-указатель по известному пассажу.**
Реалистичный live-дизайн: `find_segments` задаёт пассаж (Фатиха+сура+…, разово ~сек), а трекер быстро
(~0.2мс/тик) ведёт позицию локальным difflib-выравниванием хвоста декода к УЗКОМУ окну мини-корпуса
прочитанного вокруг указателя. Указатель монотонно ползёт вперёд: несмежные сегменты (Фатиха→Исра)
СМЕЖНЫ в мини-корпусе → **мульти-сегмент решён**; узкое окно = текущий контекст → повторяющиеся формулы
не телепортируют. **Резко точнее** k-грамм-трекера на короткоаятных сурах (см. таблицу).

**`match_align.StreamLocator` — k-грамм-трекер с lock-state** (для сценария БЕЗ известного пассажа —
холодный поиск «с нуля»):
- НЕ залочен → глобальный поиск до УВЕРЕННОЙ привязки (`confidence ≥ conf_lock`, conf = пик/(пик+2-й));
- залочен → band-трекинг в `[prior−back, prior+ahead]` (монотонно вперёд + малый возврат чтеца);
  внутри мягкий bump на «чуть впереди». Континуитет-приор = «где читаем СЕЙЧАС» биасит выбор среди
  неоднозначных мест (директива владельца: не тупо первый кандидат, а с контекстом);
- потерял сигнал `lost_max` окон → сброс в глобальный ре-поиск.

## Выводы

1. **Скорость решена** — оба трекера ~0.2мс/тик (vs 20с difflib-батч). Фундамент live есть. Тяжёлый
   difflib остаётся для точного БАТЧ-диапазона find_segments (там точность важнее скорости).
2. **Онлайн-указатель (SegmentTracker) — лучший трекер** когда пассаж известен (find_segments задал):
   7 из 9 рек 0.90-1.00, резко лучше k-грамм на короткоаятных сурах (rec12 0.27→0.99). Мульти-сегмент
   (Фатиха+Исра) решается мини-корпусом. Это основной live-механизм.
3. **k-грамм StreamLocator** — для холодного поиска БЕЗ известного пассажа (сценарий «память рядом»):
   континуитет-приор + band ведут на последовательных чтениях (0.7-0.9), но слабее на коротких аятах.
4. **Рефрен-суры — главная открытая проблема** (rec10 Ар-Рахман 0.07, отчасти rec14 0.49). Разбор ниже:
   (исходно на k-грамм, причина та же и для указателя — плотный рефрен + мелодичный бедный декод)
5. **(история k-грамм-band)** Рефрен-суры (rec10 Ар-Рахман 0.01,
   отчасти rec12/13 Вакиа). ТРАССА rec10 (`work/proto_locate.py` + отладочный вывод) показала: рефрен
   «فبأي آلاء ربكما تكذبان» УНИКАЛЕН для суры 55 (не матчит другие суры), поэтому дело НЕ в «фраза
   матчит много мест». Реальные два сбоя: **(а) рефрен ДОМИНИРУЕТ 90-символьное окно → приор застревает**
   (локатор сидит на 55:9, пока чтец уже на 55:15 — короткие distinct-аяты между рефренами не успевают
   набрать вес в окне); **(б) потеряв лок на мутном распеве, глобальный ре-поиск лочится на ЧУЖИЕ суры**
   (102:5/69:28/28:27 — шумные k-грамм-совпадения по гарбл-декоду). ⚠️ Важный вывод: **CTC-рескоринг
   идентичные рефрены НЕ развёл бы** (они и звучат одинаково) — разводит их только КОНТЕКСТ (монотонный
   трекинг). CTC-рескоринг полезен для другого — разные места с ПОХОЖИМ, но не идентичным текстом.

## Следующие шаги (в порядке ценности, по итогам честной трассы)

1. **Устойчивый монотонный трекинг вместо застревания+ложного ре-лока** (фикс rec10 (а)+(б)):
   (i) окно в СЛОВАХ/аятах, а не символах, + вес на СВЕЖИЙ хвост декода → приор двигается вперёд, не
   тонет в рефрене; (ii) «липкий» ре-лок — потеряв лок, искать СНАЧАЛА рядом с последней позицией
   (мягкий приор), в полный глобал уходить только после долгой потери → не улетать в суру 102.
2. **Окно в словах/аятах под короткоаятные суры** (rec11/12/13/14 сейчас 0.27-0.49) — символьное окно
   для коротких аятов слишком грубо; адаптивная длина.
3. **CTC-рескоринг топ-k** — для мест с ПОХОЖИМ (не идентичным) текстом: `match_align.ctc_logprob`
   (примитив есть) как «уверенность по замерам» из ТЗ. НЕ для идентичных рефренов (их решает контекст).
4. **Стрим-ASR — ОСУЩЕСТВИМОСТЬ ПОДТВЕРЖДЕНА, большого рерайта НЕ нужно.** `w2v_align.emissions()`
   УЖЕ считает аудио НЕПЕРЕКРЫВАЮЩИМИСЯ 20с-окнами независимо и конкатенирует (для 6ГБ GPU). Т.е.
   батч-эмиссии = конкатенация независимых окон → стриминг даёт ТЕ ЖЕ эмиссии, причинный/специальный
   streaming-модель НЕ нужен. Симуляция полным декодом, скармливаемым инкрементально, — верна.
   Остаётся ИНЖЕНЕРИЯ (не ресёрч): (а) фронт — захват микрофона; (б) эндпоинт: эмиссии на входящих
   чанках → греди-декод → SegmentTracker.feed(хвост) → позиция. Латентность = размер чанка (крутится
   вниз с 20с; wav2vec2 достаточно локален). Главный технический риск WI снят.
5. **Режим заучивания**: сравнение прочитанного с ОЖИДАЕМЫМ следующим аятом (band уже даёт ожидание) →
   расхождение = отклонение → подсветка красным / сигнал.
