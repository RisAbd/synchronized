# Как сейчас работает выравнивание (w2v) — полный алгоритм

> Владелец (25.07, tg_3881) попросил ОДИН РАЗ описать полностью: как работает текущий олайн, что
> детектит, что выдаёт аллайнер, по каким принципам. Плюс его идея — выравнивать «по паузам как
> якорям». Этот файл — ответ и опорная точка. Дефолтный аллайнер = **wav2vec2 (w2v)**.

## 0. Что на входе / выходе

- **Вход:** аудио чтения (одна сура/отрывок) + текст Корана (Tanzil, в `quran.db`).
- **Выход:** `word_timeline` — список точек `{surah, ayah, wi, t, t_end, rep?}`, где `t` — время начала
  слова в аудио, `t_end` — конец, `rep` — метка перечитки. По нему плеер подсвечивает слова.
- Ключевая идея: аллайнер работает **«стеной»** — склеивает все слова диапазона в один плоский
  поток и гонит по аудио непрерывно; (surah,ayah,wi) навешиваются как метки на плоский индекс.

## 1. Эмиссии (`w2v_align.emissions`) — единственный проход по нейросети

- Аудио грузим через `soundfile`, режем на окна ~20с, каждое → `Wav2Vec2ForCTC` → логиты →
  `log_softmax` → матрица **E[кадр, класс]** логарифм-вероятностей. Классы = арабский алфавит
  (~50 букв) + служебные, из них главный — **`<pad>` = "blank"** (CTC-пустышка «сейчас ничего не
  произносится / держится/тишина»). Шаг кадра ≈ **20 мс**.
- Это ВСЁ, что «видит» модель: на каждые 20 мс — распределение «какая буква звучит (или blank)».
  **Явных токенов «конец слова» или «пауза» модель НЕ выдаёт.** Пауза/тишина = длинный ран blank'ов.

## 2. Диапазон аятов (`match_align.find_range`)

- Greedy-декод эмиссий (по кадрам argmax, сжать повторы, убрать blank) → шумная строка согласных.
- Ищем, ГДЕ в Коране это читается: IDF-взвешенные k-граммы согласного скелета → пик плотности по
  сурам → границы (сура:аят..аят) с добором по покрытию. Это НЕ выравнивание — только «что за отрывок».

## 3. Выравнивание слов (`w2v_align.forced_align`) — монотонный CTC-Viterbi

- Строим **плоскую последовательность меток**: все буквы всех слов диапазона по порядку → id классов
  (буквы, которых нет в vocab, напр. надстрочный алеф, — пропускаем).
- **CTC-Viterbi** (`_ctc_viterbi`): расширенная посл-ть `[blank, l0, blank, l1, …, blank]`, переходы
  на каждом кадре: **стоять / +1 / +2** (скип blank между РАЗНЫМИ буквами). Max-путь с backpointer'ами,
  обратный ход → `path[кадр] = позиция в последовательности`. **Скип на blank запрещён** между
  одинаковыми — значит каждая буква получает ≥1 кадр → ни одно слово не «схлопывается» в ноль
  (в отличие от старого whisperx). Путь **монотонный** — только вперёд по тексту.
- **Онсет слова** = время первого кадра его ПЕРВОЙ буквы. **Слово владеет временем ДО онсета
  следующего** — т.е. долгий распев/мадд честно «висит» на слове-держателе (не обрезаем на полуслове).
- Отсюда `t` каждого слова; `t_end` = онсет следующего (или снап, см. ниже).

## 4. Паузы/тишина — ГДЕ мы их используем сейчас (ответ на идею владельца)

**Да, паузы используем — но как ВТОРИЧНЫЙ сигнал (поджатие), не как первичный якорь.** Три места:

1. **Снап к тишине (`alignbricks._snap_bounds`).** Считаем RMS-огибающую аудио (энергия по кадрам,
   в дБ), порог = шумовой пол (перцентиль) + гистерезис. Границы слова **поджимаем ВНУТРЬ к речи**:
   если хвост слова попал в тишину/паузу — обрезаем до реального звука. Это убирает «слово тянется
   через паузу». Т.е. пауза корректирует КОНЕЦ слова.
2. **Якорь перечитки (`w2v_repeats.repeat_onset`).** Когда детектим возврат в длинном span'е, начало
   назаднего повтора ставим на **конец самой длинной паузы** внутри span'а: до паузы держим
   слово-остановку, после паузы — перечитка. Это ровно «ориентируемся по паузе».
3. **blank как «держание»** в самом CTC: ран blank'ов = модель сама «понимает», что звук тянется
   или молчит; путь стоит на месте.

**Почему пауза НЕ первичный якорь (суть проблемы, которую нащупал владелец).** В таджвиде чтец
**НЕ делает паузу между каждым словом** — слова связаны (васл), пауза (вакф) только на концах
аятов/фраз/на вдохе. Поэтому «сегментируй по тишине → в каждый сегмент по слову» дало бы разбивку
на ФРАЗЫ, а не на слова; ВНУТРИ фразы (нет пауз) всё равно нужен CTC, чтобы расставить слова по
буквам. Плюс: долгий мадд по энергии похож на «держание», а иногда буква с придыханием даёт провал
энергии в СЕРЕДИНЕ слова → ложная «пауза». Поэтому первичный сигнал = буквы (CTC), а паузы —
поправка. **Идея владельца рабочая на границах ФРАЗ/аятов и на ПЕРЕЧИТКАХ** (там пауза реальна и
информативна) — и именно там мы её уже включаем (п.1, п.2). Довести можно: явный детектор фраз по
паузам как дополнительный слой поверх CTC (не вместо) — занесено в идеи.

## 5. Перечитки/возвраты (`w2v_repeats.detect`) — чего монотонный Viterbi НЕ умеет

Монотонный путь идёт только вперёд → **перечитку (чтец вернулся и прочёл снова) он выразить не может**
в принципе. Признак перечитки: span слова-остановки **аномально длинный** (≥ 2.5× медианы). Внутри:

- **greedy-путь** (как раньше): декод span → строковое сходство со словами вперёд `[i+1..j]` (FWD,
  мелодичный обгон) / назад `[ra..i]` (BACK, классический возврат). На распеве шумит.
- **CTC-likelihood (ново, 25.07):** считаем CTC-скор гипотез прямо по эмиссиям — `MADD` (буквы
  держателя, растянуты) vs `CONT` (буквы `[i..j]`). Если `CONT≫MADD` → span проглотил ПЕРВОЕ чтение
  перечитанной фразы → вставляем `[i+1..j]` с реальными Viterbi-границами. Гард против замазки:
  вставляем ТОЛЬКО если те же слова звучат и ПОСЛЕ span'а (настоящая перечитка, а не под-сегментация).
- **Пост-гард инвариант:** принимаем группу-перечитку только если она НЕ добавляет «прыжка вперёд»
  (чтец идёт вперёд по одному ИЛИ назад-возврат; резкого прыжка через слова не бывает) → `fj=0`.

## 6. Сборка (`player.build_data`)

`word_timeline` (+ `rep`) + аятные секции + вторая редакция (Diyanet, карта слов) → `data.json`.
Плеер: подсветка слова по бинарному поиску времени; на перечитках дорожка возвращается назад.

## 7. Известный предел (честно)

Greedy-декод wav2vec2 на распевном таджвиде ШУМНЫЙ (строковое сходство ≈0 даже на чистых словах;
4 абсолютных метрики оси B отвергнуты в сессиях 15–17). CTC-likelihood (п.5) устойчивее — по нему
находим под-сегментации/перечитки, но абсолютного порога «залипание vs допустимый мадд» без слуха
нет. Часть перечиток rec7 (места владельца 6/10/11/14 — возврат в ОТДЕЛЬНОЙ зоне, не внутри span'а)
пока не ловятся — нужен детект ВТОРОГО вхождения фразы в соседней зоне (BACK через регион), не только
внутри одного span'а. Это следующий заход.
